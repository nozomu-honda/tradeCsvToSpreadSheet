# src/app README

## 目的

`src/app` は、株管理ツール本体の Apps Script コードを置くディレクトリです。  
テストコードは `src/test` に分離し、実行ロジックと検証ロジックを明確に分けます。

---

## 役割

このディレクトリには、以下のような **本番実行対象のコード** を置きます。

- Webアプリの入口
- CSV / スプレッドシート入力の取込
- DB入出力
- 4シート生成ロジック
- シート書き込み
- 各種ユーティリティ
- 設定定数

---

## 想定ファイル

### `web.gs`
Webアプリ公開用の入口です。

主な責務:
- `doGet`
- HTML テンプレートへの値受け渡し
- フロントから呼ばれる公開関数の受付
- UI 操作とアプリ本体ロジックの接続

### `import.gs`
入力データの読込を担当します。

主な責務:
- CSVリンク読込
- CSVテキスト読込
- スプレッドシート読込
- 一次受け枠作成
- 入力シート自動判定
- 手入力列の検証

### `db.gs`
DB相当のスプレッドシート入出力を担当します。

主な責務:
- 追加先DBの選択
- DBスプレッドシート取得 / 作成
- レコード追記
- rowHash による重複回避
- 取込履歴管理
- ロールバック
- DBリセット
- DB互換性チェック

### `parser.gs`
入力シートから業務レコードへ変換する責務を持ちます。

主な責務:
- ヘッダー判定
- ヘッダー整合性チェック
- 明細行の読込
- 型変換前の入力構造解釈

### `builder.gs`
業務ロジックの中核です。  
入力レコードから出力用行データを構築します。

主な責務:
- 取引シート行生成
- 金銭残高シート行生成
- 平均取得単価計算
- 簿価計算
- 銘柄ごとの残高計算
- 並び順制御
- アラート生成

### `writer.gs`
生成済みデータをスプレッドシートへ書き込む責務を持ちます。

主な責務:
- シート作成 / 初期化
- 値書き込み
- 列非表示
- 数値書式
- 条件付き書式
- 強調表示

### `config.gs`
設定値と固定定義をまとめます。

主な責務:
- 出力シート名
- DBシート名
- 各種ヘッダー定義
- 表示・運用設定
- 追加先DB設定

### `utils.gs`
共通ユーティリティです。

主な責務:
- 日付変換
- 数値変換
- 通貨正規化
- 空値 / 0 正規化
- 文字列補助
- 小さな共通関数

## 依存関係の考え方

依存はできるだけ次の向きに寄せます。

- `web.gs` → `import.gs` / `db.gs`
- `import.gs` → `parser.gs` / `db.gs` / `builder.gs`
- `db.gs` → `config.gs` / `utils.gs`
- `builder.gs` → `config.gs` / `utils.gs`
- `writer.gs` → `config.gs` / `utils.gs`
- `parser.gs` → `config.gs` / `utils.gs`

### 原則
- `utils.gs` は下位の共通部品として使う
- `config.gs` は定義置き場として使う
- `builder.gs` に UI 都合を入れすぎない
- `web.gs` に業務計算ロジックを書かない
- `test` からしか使わない補助関数は `src/test` に置く

---

## 命名ルール

### 基本
- Apps Script 内部専用関数は末尾 `_`
- 公開入口関数は用途が分かる名前にする
- 日本語ヘッダー文字列は定数化できるものは定数化する

### 例
- `readInputRecords_`
- `buildTradeRows_`
- `appendRecordsToDb_`
- `runFromWebApp`
- `resetDbFromWebApp`

---

## 実装ルール

### 1. 役割をまたがない
たとえば:
- `web.gs` で直接計算しない
- `builder.gs` で直接 UI エラーメッセージ制御をしすぎない
- `writer.gs` で入力解釈しない

### 2. ヘッダー差異は黙って吸収しない
入力仕様が崩れたときは、可能な限り明示エラーにします。

### 3. 手入力列は通常列と同じく明示管理
追加列は
- 読込
- バリデーション
- rowHash
- DB保存
- 出力反映

まで一貫して扱います。

### 4. DBスキーマ変更時は互換性を意識
列追加・順序変更時は
- `DB_HEADERS`
- 読込
- 書込
- テスト
- 仕様書

を同時に更新します。

## ディレクトリ分割方針

### `src/app`
本番コード

### `src/test`
テストコード

今後さらに分ける場合は、必要になってから以下のように細分化します。

- `src/app/core`
- `src/app/io`
- `src/app/ui`
- `src/app/shared`

ただし、現時点では分割しすぎず `src/app` 配下フラットで管理する方が運用しやすいです。

---

## 変更時チェックリスト

新しい仕様変更を入れるときは、少なくとも以下を確認します。

- 本体コード更新
- テスト更新
- DB列更新の有無確認
- README / docs 更新
- Web UI 変更の有無確認
- ロールバック影響確認

---

## 補足

このプロジェクトでは、  
**「入力」「計算」「保存」「表示」を分離すること** を優先します。

そのため、迷ったときは次の基準で置き場所を決めます。

- 入力を読む話 → `import.gs` / `parser.gs`
- 計算する話 → `builder.gs`
- DBへ保存する話 → `db.gs`
- シートへ書く話 → `writer.gs`
- UIから呼ぶ話 → `web.gs`
- 共通小物 → `utils.gs`
- 固定定義 → `config.gs`
